This project is a benchmark corpus for JSON Schema inclusion checking (does schema A subsume schema B?) for draft 2020-12, plus the Python code that builds it.

## Tooling

Everything runs through `uv`. `make ci` runs what CI runs on a pull request: `ruff check`, `ruff format --check`, `ty check`, `check-jsonschema` on the configuration files, `datamodel-codegen --check` on the models generated from their schemas, `pytest`, and for the adapters under `checkers/`, `cargo fmt --check` and `cargo clippy` on the Rust ones and `ty check` on the Python ones, each against its own environment. `make format` fixes what ruff and `cargo fmt` can fix. Configuration lives in `pyproject.toml`; CI is `.github/workflows/ci.yml` (tests on Python 3.14, which read every case of the corpus and take under a minute). `.github/workflows/release.yml` runs release-please, configured in `release-please-config.json`: it keeps a release pull request open, and publishes the release when that pull request is merged. `.github/workflows/pr-title.yml` checks the title of every pull request. `.github/workflows/comparison.yml` runs the checkers under `checkers/` over the corpus: over every task after a release or when started by hand, and over a sample when started by hand with a limit. It does not run on a pull request. `.github/workflows/subsumes-release.yml` pins the adapters of subsumes to a release of it, in a pull request; a release of subsumes starts it with a `repository_dispatch` event, and a release here sends subsumes the event `benchmark-released` in turn. Both are sent as the GitHub App of `PR_BOT_CLIENT_ID`.

## Rules

- The built package holds the corpus as one file, `src/subsumes_benchmark/corpus.tar.zst`, and no other benchmark data. The file is not committed: the release packs it from `corpus/` before it builds the package, with `make archive`, and attaches the same file to the release. The package is published to PyPI with every release, as the command `subsumes-benchmark`, which unpacks the corpus and runs a checker over it.
- The package is licensed `MIT AND GPL-3.0-only`: the code is MIT, and the corpus in it keeps the licences of its sources. The folder of each collection under `corpus/` holds the text as `LICENSE`, and those go into the package as licence files. A collection from a source under another licence needs that licence in `pyproject.toml` too.
- Every change reaches `main` through a pull request; a ruleset rejects a direct push.
- Commit messages and pull request titles follow the Conventional Commits format.
- Pull requests are squash-merged, so the PR title becomes the commit message on `main`.
- The titles decide the next version, so the type says what a change does to the corpus: `!` when a reader has to change, `feat` when a label, a schema or the set of cases changes, even to correct a mistake, and `fix` for anything else worth a release. `CONTRIBUTING.md` has the table.
- The release pull request raises the version. Never change the version in `pyproject.toml`, `uv.lock` or `.release-please-manifest.json` by hand.
- A case is `corpus/<origin>/<collection>/<name>.json`, and no file of the corpus lies deeper. Its id is that path without the extension. The origin is the citation key of the work that first published the pairs as inclusion questions: the first author's last name and the year. It is not the source that the build reads them from, and `collections.json` names both for every collection. The build writes `corpus/collections.json` from it, which says of every collection what a reader of the corpus needs: the origin with its citation, the repository and commit of the source, the licence and where the labels come from.
- `corpus/` is generated, except its `README.md`, which is written by hand and which a build leaves as it is; never edit anything else in it by hand. Every link in that page to something outside `corpus/` is a full URL, since the page travels in the archive. Change `collections.json`, `overrides.json`, `derived.json` or the code under `src/`, then run `make corpus` (after `make sources`, once) and commit the result.
- A label that departs from upstream's needs an entry under `override` in `overrides.json` with the reason. Nothing else may change a label. For a case built from the official test suite, upstream's label is what the suite's expected result gives.
- No two cases hold the same two schemas, in either order. Of the upstream cases that do, the build keeps the one whose id sorts first, gives it what the others say about either direction and their notes, and lists their upstream files under `duplicates`. `overrides.json` and its exclusions name upstream cases; `derived.json` names cases of the corpus.
- A label where a case has none comes from `derived.json`, with what shows it. `subsumes-benchmark derive` writes the file from runs of checkers with `--unlabelled`; never edit it by hand. A label is `false` only with a counterexample that both validators of `subsumes_benchmark.validation` confirm, and `true` only where two checkers say yes, none says no, and the schemas use neither a pattern nor a format. One checker's yes is never a label, and a case that `overrides.json` lists gets none.
- Every schema in the corpus is valid draft 2020-12 and every reference in it resolves. The schema of a case requires the first, by referencing the metaschema, and a keyword that asserts nothing, such as `deprecated`, is no exception. An upstream case that is not is left out through an entry under `exclude` in `overrides.json`, with the reason. So is a test case of the official test suite whose expected results are not those of draft 2020-12 with `format` asserted.
- The labels hold for draft 2020-12 with `format` asserted and patterns read as ECMA-262 regular expressions with the `u` flag, which is what the specification recommends. Do not use Python's `re` to decide what a pattern matches, nor Python's format checkers to decide what a format accepts; `subsumes_benchmark.validation` has the validator.
- In a case, `a` is the schema that should accept everything and `b` the one whose instances must be accepted. Keep that orientation in every name: `a_subsumes_b`, `subsumes(a, b)`.
- The build uses Pydantic, which reads the configuration files, and otherwise the standard library only. Running a checker (`subsumes_benchmark.compare`) uses `jsonschema-rs` besides, which validates the counterexamples that a checker gives; its version is pinned exactly, since it decides which of them count. What only the tests need goes in the `dev` dependency group, and what only the report needs in the extra `report`, so that an installed package can have it. What validating an instance as the labels read a schema needs besides goes in the `validation` group, which `dev` includes: the tests need it, and so does deriving a label, which is done in a checkout.
- `README.md` is the page of the repository and of the package on PyPI, so every link and picture in it is a full URL. It stays short: what the benchmark is, the results, the collections, and how to get the corpus and run a checker. What a case holds and what the labels mean is in `corpus/README.md`, how the corpus is built in `docs/construction.md`, the checkers, the commands and the protocol in `checkers/README.md`, and development in `CONTRIBUTING.md`.
- Two parts of `README.md` are written from data, each between two marker lines: the table of the collections by `make corpus`, and the table of the checkers by the `Comparison` workflow. Both put a Markdown table there with `scripts/readme-part.sh`, and no Python writes into a README: `python -m subsumes_benchmark.table` prints the first table, and `subsumes-benchmark report` writes the second as `comparison/results.md`, next to the plots. No other page states a count that the corpus decides, except the tables of `docs/construction.md`.
- The command takes every path relative to the working directory and assumes no checkout around it, since it also runs as an installed package.
- `comparison/` and the part of the README between the `comparison` markers are written by the `Comparison` workflow, and the part between the `collections` markers by `make corpus`; never edit them by hand.
- `collections.json`, `overrides.json`, `derived.json` and every `checker.json` each name their schema under `schemas/` in `$schema`. The schemas are written by hand and decide what a valid file is. The three lines of the protocol have schemas too, `ready.schema.json`, `request.schema.json` and `reply.schema.json`, and so have the two files of a run, `result.schema.json` for a line of `results.jsonl` and `run.schema.json` for `run.json`. A change to the protocol or to those files starts in its schema.
- In those five schemas, a key that does not apply is left out, and `null` is written only where it is a value: for an answer that the checker declined, for a label that the corpus does not have, and for a counterexample that is `null`. An answer is `true`, `false` or `null`, as a label is. The same key means the same thing in all of them: `answer`, `expected`, `failure`, `seconds` for the time of the checker on one task, `wall_seconds` for a time that the runner waited, `message` for a text for a person, `reason` for what the declined tasks are counted by.
- What two of those schemas share is written out in both, since the generator takes one schema at a time: the keys of a reply in a result, and the description of a checker in a run. `tests/test_protocol.py` fails when the copies differ.
- A model that is generated from a schema reads a little more than the schema allows, such as `null` for a key that is left out. Nothing is made of that. What the runner writes is what the schema allows, which the tests hold. So does `schemas/case.schema.json` for a case; the build copies it to `corpus/case.schema.json`, which every case names, and the list of features is the one in it. It references the metaschema of draft 2020-12, and `schemas/generator/` holds what the generator reads in its place. `src/subsumes_benchmark/generated/` holds the Pydantic models that read the files, generated from the schemas by `datamodel-codegen`; never edit it by hand. Change a schema, then run `make models` and commit the result. What a schema cannot say goes in a class that extends the generated one. `make config` holds each file against its schema with `check-jsonschema` and checks that the generated models are current, as CI does.
- A checker is used from a package index at a pinned version wherever it is published to one. The `version` in its `checker.json` is the version its folder pins.
- `checkers/rwg/` is GPL-3.0, because it is compiled together with RWG. Nothing outside that folder may link to RWG.

## Coding Conventions

- Use the narrowest practical type.
- `Sequence[T]` for variable-length collections. Use `tuple[...]` only for fixed-length positional data like `tuple[str, int]`, or where you actually need tuple behaviour. Don't write `tuple[T, ...]`.
- `Literal[...]` for small closed sets instead of bare `str`.
- PEP 695 type parameters: `def f[T: Base](x: T) -> T`, not a separate `TypeVar`. Applies to generic classes, functions, and aliases.
- Don't annotate with `dict` or `Any` when it is not really necessary. Don't annotate with `Any` when a better type is available or would be easy to create; a `dataclass` is usually that better type. JSON values are `subsumes_benchmark.Json`.
- Dataclasses for data holders instead of hand-written `__init__` and `__repr__`.
- `match` for closed-set dispatch on a `Literal` or a sealed class hierarchy, with a `case _: assert_never(x)` arm, so exhaustiveness is a typecheck failure rather than a silent fall-through.
- Classmethod factories over module-level constructors: `ClassName.create(...) -> Self`, not `_create_class_name(...)`.
- Docstrings use Google style. Omit types from `Args`/`Returns` and skip `Raises` unless crucial.
